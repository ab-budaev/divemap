## 1. Локальная проверка коммит-сообщений (Infra)

- [x] 1.1 [Infra] Установить pre-commit как инструмент разработчика (`uv tool install pre-commit`). Критерий приёмки: `pre-commit --version` выполняется успешно.
- [x] 1.2 [Infra] Создать `.pre-commit-config.yaml` в корне репозитория: хук `conventional-pre-commit` (репозиторий `https://github.com/compilerla/conventional-pre-commit`, пин версии по тегу), стадия `commit-msg`. Критерий приёмки: `pre-commit validate-config` проходит без ошибок.
- [x] 1.3 [Infra] Добавить в корневой `Makefile` цель `hooks`, выполняющую `pre-commit install --hook-type commit-msg`. Критерий приёмки: `make hooks` завершается успешно; повторный запуск `make hooks` также успешен (идемпотентность).
- [x] 1.4 [Infra] Проверить хук end-to-end локально: `git commit -m "добавил запись"` отклоняется с ошибкой формата, `git commit -m "feat: add dive journal entry"` создаётся. Критерий приёмки: оба сценария воспроизводятся, текст ошибки указывает на несоответствие conventional commits. (Тестовые коммиты делать на временной ветке или с последующим `--amend`/сбросом, не засоряя историю.)

## 2. Проверка коммит-сообщений в CI (Infra)

- [x] 2.1 [Infra] Создать `.github/workflows/commits.yml` в корне репозитория: триггеры `push` и `pull_request`, checkout с `fetch-depth: 0`, установка `conventional-pre-commit` из PyPI (с пином версии). Критерий приёмки: workflow синтаксически валиден (`actionlint` или успешный запуск в GitHub Actions).
- [x] 2.2 [Infra] Реализовать в workflow определение диапазона коммитов: для push — `before..after` из события, для PR — `base..head`; проверка каждого сообщения из `git log --no-merges --format=%B` через `conventional-pre-commit`, при нарушении — вывод проблемного сообщения и exit code != 0. Критерий приёмки: тестовый push с коммитом «fix stuff» на временной ветке роняет job с понятным логом; push с корректными коммитами проходит.
- [x] 2.3 [Infra] Убедиться, что проверка для PR работает: на тестовом PR статус проверки отображается неуспешным при некорректном коммите и успешным после исправления. Критерий приёмки: оба состояния воспроизведены на тестовом PR (PR закрыть без merge после проверки).
