# Proposal

## Мотивация

У divemap есть работающий локальный фундамент бэкенда (FastAPI + PostgreSQL, поднимается одной командой), но нет фронтенда вообще: ни каркаса, ни инструментов сборки, ни способа отдать интерфейс пользователю. Все функциональные этапы MVP (карта и места, журнал погружений, фото) — клиентские по своей природе и не могут начаться без фронтенд-каркаса.

При этом владелец проекта — бэкенд-разработчик, не знакомый с современным фронтенд-ландшафтом. Каркас должен быть минимальным и понятным: без лишних абстракций и библиотек «на вырост», с явной структурой каталогов и прозрачной схемой запуска. Это изменение создаёт такой каркас и фиксирует технические решения, чтобы этапы 2–4 строились на нём без пересмотра фундамента.

Фронтенд и бэкенд сознательно разделяются на уровне сборки и деплоя: каждый собирается в собственный Docker-образ и релизится независимо. Бэкенд остаётся чистым API-сервисом и не занимается раздачей статики.

## Пользовательские сценарии

Я как разработчик:

- хочу одной командой из корня репозитория поднять всё окружение разработки (бэкенд и фронтенд), сохраняя возможность запускать каждую часть по отдельности.
- хочу, чтобы dev-сервер фронтенда работал с hot-reload и проксировал API-запросы на локальный бэкенд, чтобы правки API были видны в UI сразу, без сборок и перезапусков.
- хочу понятную структуру каталогов фронтенда (где живут страницы, компоненты, работа с API), чтобы как бэкендер ориентироваться в этой части проекта.
- хочу, чтобы фронтенд собирался в отдельный Docker-образ, независимый от образа бэкенда, чтобы релизить и перезапускать их по отдельности.
- хочу типизированный клиент API, чтобы контракт с бэкендом был виден в коде и ловился компилятором.
- хочу проверку качества кода (линтер, проверка типов) в CI, чтобы фронтенд не деградировал по мере роста.

## Что меняется

Добавлено:

- Каталог `frontend/` с каркасом React + TypeScript на Vite: строгий `tsconfig`, линтер, скрипты сборки и запуска
- Структура каталогов и слой доступа к API (типизированный fetch-клиент + TanStack Query для серверного состояния) — готовые к наполнению в этапах 2–4
- Dev-сервер с проксированием `/api` на локальный бэкенд
- Корневой `Makefile` расширен целями запуска: `up` поднимает всё окружение (бэкенд + фронтенд) одной командой, отдельные цели запускают бэкенд и фронтенд по отдельности; npm-зависимости устанавливаются автоматически при первом запуске
- `frontend/Dockerfile`: отдельный образ фронтенда (nginx + собранная статика), независимый от образа бэкенда
- CI-проверки фронтенда (линтер, проверка типов, сборка)
- Документация по запуску фронтенда в README

Изменено:

- Корневой `Makefile` — сейчас содержит только установку git-хуков, дополняется целями запуска dev-окружения
- README — инструкции по запуску фронтенда

Удалено: ничего.

Явно отложено за пределы этого изменения:

- Маршрутизация запросов между фронтендом и API в продакшене (Caddy/reverse proxy, пути `/api` vs статика), деплой на VPS, домен и TLS — отдельное изменение про инфраструктуру; это изменение лишь готовит образ фронтенда
- Карта и библиотека отображения карты (Leaflet/react-leaflet) — этап «Карта + Spot»
- Маршрутизация внутри приложения: по продуктовой спецификации экран один, панели поверх карты; роутер не нужен и не добавляется
- Глобальный клиентский state-менеджер (Zustand/Redux): по исследованию для этого MVP достаточно TanStack Query (серверное состояние) + локального состояния компонентов; решение зафиксировано в design.md и пересматривается только при появлении реальной потребности
- Функциональные экраны (создание места, карточка, журнал) — этапы 2–4

## Возможности

### Новые возможности

- `tech/frontend`: операционное поведение фронтенд-части — запуск dev-окружения с проксированием API, production-сборка в отдельный Docker-образ со статикой, проверки качества кода в CI.

### Изменённые возможности

Нет: существующие требования (`tech/backend`, `tech/general`, `product/api/users`) не меняются — бэкенд остаётся чистым API-сервисом, его поведение и образ не затрагиваются.

## Влияние

- Появляется каталог `frontend/` с собственным toolchain (Node.js, npm) и собственным `Dockerfile` — новая зависимость окружения разработки и новый артефакт сборки
- Бэкенд, его образ и `compose.yml` не меняются: фронтенд в dev-режиме живёт отдельным процессом (Vite, порт 5173) рядом с бэкендом (порт 8000)
- Связка двух образов в продакшене (reverse proxy, маршрутизация `/api`) остаётся открытой для изменения про инфраструктуру
- Существующие API-эндпоинты и база данных не затрагиваются
