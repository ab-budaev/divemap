# Proposal

## Мотивация

Сейчас в системе нет понятия пользователя: база данных пустая (initial-миграция не создаёт таблиц), а единственный эндпоинт — служебный `/health`. Для дальнейшей работы с персональными данными (места, погружения, фото) нужна опорная сущность «пользователь» и точка входа в API, отдающая информацию о текущем пользователе.

Это изменение закладывает фундамент: модель данных пользователя в PostgreSQL и REST-ручку получения информации об авторизованном пользователе. Схема аутентификации/авторизации сознательно выносится за рамки — ручка проектируется так, чтобы механизм определения «текущего пользователя» подменялся одной зависимостью, когда auth появится.

Допущение: запрос владельца явно вводит сущность пользователя, хотя AGENTS.md относил мультипользовательность к «не в MVP». Трактуем это как осознанное расширение скоупа со стороны владельца.

## Пользовательские сценарии

Я как разработчик:

- хочу хранить пользователей в базе данных, чтобы у системы была опорная сущность для привязки данных (места, погружения);
- хочу получать информацию о текущем пользователе через API, чтобы фронтенд мог отобразить профиль без знания внутреннего устройства хранения;
- хочу отложить выбор схемы аутентификации, чтобы не блокировать моделирование данных и API на недоступных пока решениях.

## Что меняется

Добавлено:

- Таблица `users` в PostgreSQL (через Alembic-миграцию) и соответствующая ORM-модель SQLAlchemy 2.0.
- Доменная сущность пользователя и репозиторий в слоях `domain` / `infrastructure` / `application` (по принятой DDD-структуре `backend/src`).
- REST-эндпоинт получения информации об авторизованном пользователе (`GET /users/me`).
- Зависимость FastAPI `get_current_user` — точка расширения для будущей аутентификации; в рамках этого изменения — заглушка, возвращающая пользователя по умолчанию.

Изменено:

- Регистрация роутеров в `backend/src/api/app.py` — подключение роутера пользователей.

Удалено:

- Ничего.

Явно отложено за пределы этого изменения:

- Схема аутентификации и авторизации (логин, токены, сессии, регистрация).
- CRUD-операции над пользователями (создание, редактирование, удаление) — кроме технической возможности завести пользователя по умолчанию для работы заглушки.
- Привязка существующих и будущих сущностей (Spot, Dive) к пользователю.

## Возможности

### Новые возможности

- `product/api/users`: хранение пользователей в БД и выдача информации об авторизованном пользователе через API.

### Изменённые возможности

- Нет.

## Влияние

- **Код**: новые модули в `backend/src/domain`, `backend/src/application`, `backend/src/infrastructure`, `backend/src/api/routers`; точечное изменение `backend/src/api/app.py`.
- **База данных**: новая миграция Alembic, создающая таблицу `users`; обратно совместимо (данных нет).
- **API**: новый эндпоинт `GET /users/me`; существующий `/health` не затрагивается.
- **Зависимости**: новых внешних зависимостей не требуется (SQLAlchemy, Alembic, FastAPI уже в проекте).
