# Стиль кода

Правила обязательны для любого кода, который ты пишешь или правишь в этом проекте.

## Никаких комментариев

Не пиши комментарии в коде. Совсем. Никаких:

- поясняющих (`// проверяем, что пользователь авторизован`)
- структурных (`# --- Helpers ---`)
- исторических (`// раньше тут было другое поведение`)
- TODO/FIXME — вместо них скажи владельцу в ответе
- docstring-ов по умолчанию — только если они используются как документация API (например, для Swagger в FastAPI) или уже приняты в этом файле

Код должен объяснять себя сам: через имена, типы и структуру. Если место кажется непонятным без комментария — перепиши код так, чтобы стал понятным (вынести в функцию с говорящим именем, переименовать переменную), а не комментируй.

Это касается и директив линтера (`# noqa`, `# type: ignore` и т.п.): если подавление warning-а реально нужно, оформи его в конфиге линтера (per-file-ignores, overrides), а не комментарием в коде.

Исключение — только явный запрос владельца на конкретный комментарий.

При правке существующего кода не добавляй комментарии и не удаляй чужие массово; удали комментарий только если он описывает код, который ты меняешь.

## Лаконичность и простота

- Пиши минимум кода, решающего задачу. Не пиши код «на будущее» и под гипотетические сценарии.
- Простые прямые решения важнее абстракций. Не вводи интерфейсы, фабрики, слои и конфигурацию там, где хватает одной функции.
- Одна функция — одна задача, коротко. Если функция разрослась — раздели, а не комментируй секции.
- Имена — говорящие и конкретные (`spots_by_date`, не `data`); короткие имена (`i`, `e`) допустимы в очевидных местах.
- Не добавляй обработку ошибок там, где она ничего не даёт: не лови исключение, чтобы просто перебросить или залогировать и забыть.
- Соответствуй идиомам окружающего кода и версиям библиотек из манифеста проекта, а не привычкам из других стеков.
